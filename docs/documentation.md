# 开发文档的组织与维护

本文记录 2026-10-17 文档整理讨论确定的组织规则。目标是：新开发者只读 architecture 和相关 design，就能理解当前设计，无须先遍历 ADR。此次整理只改变文档，不改变系统行为、公开接口或既有决策。

## 内容归属

| 文档 | 负责的内容 | 不承担的内容 |
|---|---|---|
| vision | 目标、价值判断、方向 | 具体接口与施工进度 |
| architecture | 系统概念、包与进程边界、跨领域约束、协作链路、数据所有权 | 组件算法、完整目录树、施工流水 |
| design | 按领域组织的当前模型、约束、协作机制和必要理由 | 以历史修订顺序组织的正文 |
| decisions | 一次选择的背景、备选、理由、代价和替代关系 | 当前设计的唯一说明、持续追加的验收日志 |
| reference | 精确的格式、字段、参数、错误与配置 | 未实现方案 |
| guides | 完成具体任务的操作步骤 | 架构规范 |
| Issue / PR | 施工切片、验收记录、过程事故 | 当前设计的唯一事实来源 |

## 约束与实现

系统级约束是跨领域开发必须共同遵守的边界；领域约束在相应 design 完整定义，效力不因其位置而降低。当前实现说明已采用的技术和结构，不将数量、默认值、类名等自动提升为永久约束。改变已接受的技术选择仍需评估、讨论并同步文档。

每条规则有一处完整定义，其他文档只概括并说明本域如何遵守。architecture 区分「系统约束」和「当前实现」，design 区分「领域约束」「当前机制」和「未实施方向」。已拍板不等于已实现；未实施方案不得混入当前机制或 reference。

## 决策记录

保留 ADR 编号和路径，不按重要程度改名或搬迁。通过领域索引展示影响范围和替代关系；范围、稳定性、有效状态是不同属性，不合成一个重要等级。当前有效规则必须吸收到 architecture/design，ADR 是其历史来源。

历史选择和理由保留；允许更新状态、替代关系及指向当前设计的链接。部分条款被替代时明确指出范围，不能将整篇一律标为有效或废止。新 ADR 记录跨领域边界、领域模型或重要取舍的变化；普通修复和实现步骤由 design 与 PR 记录即可，不因每次改动机械新增 ADR。

已有 ADR 中的验收记录作为历史证据保留，不继续累加；新的测试数量和施工事故写入 PR。当前 design 中被废止的正文转为简短历史来源链接，不让读者通过删除线和补注计算现行规则。

## 更新流程

1. 方向讨论拍板后，先更新决策记录或方案；注明接受状态与实施状态。
2. 实施时同步更新 architecture、相关 design 和 reference；完成的计划转为当前机制，未实施方向独立列出。
3. 变更跨域接口时核对生产者和消费者文档；同一契约只在其所属领域完整定义。
4. 验证本地链接、生成 reference 新鲜度与项目质量门。文档校验不代替运行时验证；报告实际执行的检查和限制。
