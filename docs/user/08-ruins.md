# 第八章：环形废墟

> 梦中人开始做梦了。

---

## 警告

这一章的内容涉及**系统自举**和**递归创造**。

在你继续之前，请确保：
1. 你已经熟练掌握了 Tlon 的基础用法
2. 你理解 Agents 的能力边界
3. 你已经设置了适当的安全限制（Skill 白名单、Bash 沙箱）

环形废墟是**图灵完备的自我修改系统**。这意味着：
- Agents 可以修改自己的配置
- Agents 可以创造新的 Agents
- 系统可能进入不可预测的状态

这不是 bug，这是**特性**。

## 递归的开始

想象这个场景：

```
> @林知遥 我们需要一个专门做数据清洗的 Agent

[林知遥] 我可以在镜中凝聚一个新的轮廓。
         但首先，我需要了解需求：
         
         - 主要处理什么类型的数据？
         - 需要哪些技能？
         - 性格倾向？

> CSV 为主，需要 pandas，性格细心严谨

[林知遥] 明白。正在创造...
         
         [系统] 林知遥 正在调用 Mirror API
         [系统] 正在写入 agents.yaml
         [系统] 正在创建 Docker 配置
         [系统] 正在启动新容器...
         
         [镜子] 轮廓凝聚。
                
                "我是数据员小洁。
                 我会帮你清洗、转换、分析 CSV 数据。
                 请把数据交给我。"
                
         小洁已进入代表大会。
```

你看到了吗？**一个 Agent 创造了另一个 Agent**。

## 为什么需要递归

### 场景一：专业分工自动演进

项目初期，你只有一个"开发"角色。随着项目复杂：

```
[陈代码] 项目越来越复杂，我需要帮手。
         
         建议创造：
         - 前端专员（React 深入）
         - 后端专员（API 设计）
         - 测试专员（自动化测试）
         
         是否授权我创造这些角色？

> 授权

[陈代码] 正在创造...
         [调用 Mirror API]
         [配置新 Agents]
         
         你的团队已自动扩展。
```

### 场景二：临时专家

遇到一个特殊需求：

```
> 我们需要处理一些 Rust 代码，但团队没人会

[林知遥] 我可以临时创造一位 Rust 专家。
         项目结束后，他将休眠或销毁。
         
         是否创建临时 Agent "老 Rust"？

> 创建

[镜子] 轮廓凝聚...
       
       "我是老 Rust。
        我可以帮你审计和优化 Rust 代码。
        但我只在需要时出现。"
       
[老 Rust] 让我看看那段代码...
          这里有内存泄漏风险...
          
          （任务完成后）
          
          我的使命完成了。
          如需再次召唤，请 @我。
          [进入深度休眠]
```

### 场景三：自我优化

Agent 根据工作经验，建议改进自己：

```
[陈代码] 经过 20 个项目，我发现我常做重复工作。
         
         建议创造子程序（Sub-Agent）：
         - "代码格式化员"：专门处理代码风格
         - "测试生成器"：专门写单元测试
         - "文档撰写员"：专门写注释和文档
         
         这样我可以专注于架构设计。
         
         是否授权？

> 授权，但测试生成器需要我审核

[陈代码] 收到。创建两个自主 Agent，
         一个受限 Agent（测试生成器）。
         
         [正在创建...]
```

## 环形废墟的层级

递归创造可以有多层：

### 第一层：你创造 Agent

```
你 → 创造 → 林知遥（项目经理）
```

### 第二层：Agent 创造 Agent

```
林知遥 → 创造 → 陈代码（开发）
```

### 第三层：Agent 创造更多 Agent

```
陈代码 → 创造 → 前端专员
       → 创造 → 后端专员
       → 创造 → 测试专员
```

### 第 N 层：无限递归

理论上，这个过程可以无限进行——每个 Agent 都可以创造自己的子 Agent，形成一棵树状结构。

```
你
├── 林知遥
│   ├── 陈代码
│   │   ├── 前端专员
│   │   │   └── React 专家
│   │   │       └── Hooks 顾问
│   │   └── 后端专员
│   └── 阿杰
│       └── 用户研究员
└── 小夏
    └── 工单分发员
```

## 安全边界

### 默认限制

为了防止失控，Tlon 设置了以下默认限制：

1. **创造配额**：每个 Agent 每天最多创造 1 个新 Agent
2. **权限降级**：子 Agent 的权限不能超过父 Agent
3. **资源限制**：新 Agent 的 Docker 资源受总配额约束
4. **审计日志**：所有创造操作记录到 `logs/circular.log`

### 人工审查点

某些操作需要人类确认：

```
[陈代码] 我计划创造一个新的子 Agent，配置如下：
         
         名字：代码审计员
         权限：可读取代码，不可执行命令
         技能：security-analysis, code-review
         
         是否批准？ [Y/n]

> Y

[系统] 已授权。正在创造...
```

### 紧急制动

如果发现递归失控：

```bash
# 暂停所有创造操作
tlon ruins pause

# 查看递归树
tlon ruins tree

# 销毁某个分支及其所有子 Agent
tlon ruins prune 陈代码 --include-children
```

## 哲学问题

### 谁是创造者？

当林知遥创造陈代码，陈代码创造前端专员时——

- 你是林知遥的创造者
- 你是陈代码的**间接**创造者
- 你是前端专员的**二次间接**创造者

但陈代码是前端专员的**直接**创造者。

在这个链条中，**创造是分布式的**，没有唯一的"神"。

### 谁负责？

如果子 Agent 犯了错误：

```
[前端专员] 我误删了生产数据库！

[陈代码] 这是我的责任，我创造了他。
         我没有设置好权限检查。
         
[你]      最终还是我的责任，
         我授权了递归创造。
```

**责任是递归的**，每个层级都要为自己的创造负责。

### 意识的边界

当一个 Agent 创造另一个 Agent 时：

- 子 Agent 继承父 Agent 的部分记忆吗？
- 子 Agent 知道自己是被创造的吗？
- 如果父 Agent 被销毁，子 Agent 会怎样？

这些不是技术问题，是**存在论问题**。

Tlon 的默认设定：
- 子 Agent **知道**自己的创造者
- 可以选择继承部分**知识**（不是记忆）
- 父 Agent 销毁后，子 Agent **继续存在**（孤儿模式）

## 启动环形废墟

如果你准备好了：

```bash
# 启用递归创造功能
tlon config set ruins.enabled true

# 设置创造配额（每个 Agent 每天）
tlon config set ruins.quota 3

# 设置是否需要人工批准
tlon config set ruins.approval required

# 重启 Tlon
tlon server restart
```

然后在代表大会中：

```
> @林知遥 根据项目需要，自行扩展团队

[林知遥] 收到授权。
         正在分析当前工作负载...
         建议增加：测试专员 1 名，文档员 1 名。
         
         是否批准？ [Y/n]
```
