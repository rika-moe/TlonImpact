# 第七章：花园

> 每一次 fork，都是时间的分叉。

---

## 平行的可能性

在博尔赫斯的故事里，时间不是一条线，而是一个花园——每一个岔路口都通向不同的未来。

在 Tlon 里，你的代码也是如此。

当你面临一个技术决策时，不再需要纠结"选 A 还是选 B"。你可以**同时走两条路**。

---

## 花园中的工作流

### 场景：技术方案对比

你需要决定缓存方案，但不确定哪个更好。

```
> @林知遥 我想对比 Redis 和本地内存两种缓存方案

[林知遥] 明白，我创建两条时间线：
         
         🌿 路径 A：Redis 方案
            @陈代码-A 实现 Redis 缓存
            
         🌿 路径 B：本地内存方案
            @陈代码-B 实现本地缓存
         
         两个分支会并行开发，
         完成后我们对比性能和复杂度。
```

然后林知遥协调团队在两个分支上并行工作——先探索 Redis 方案，再切换到本地内存方案评估。两条路径互不干扰，同时推进。

几小时后：

```
[林知遥] 两条路径都已完成。
         
         🌿 路径 A（Redis）：
            - 响应时间：12ms
            - 代码复杂度：中等
            - 可扩展性：高
            
         🌿 路径 B（本地内存）：
            - 响应时间：5ms
            - 代码复杂度：低
            - 可扩展性：低（单机）
            
         建议：如果单机部署选 B，分布式选 A。
         
         您倾向哪条路径？
```

你选择一条，另一条成为**未被选择的平行宇宙**——但它存在过，留下了知识。

### 场景：A/B 测试

```
> @阿杰 设计两种登录页面，做 A/B 测试

[阿杰] 创建两条路径：
       
       🌿 分支 feature/login-a：
          设计：简约风格，单字段输入
          
       🌿 分支 feature/login-b：
          设计：分步引导，动画丰富
          
       @小雅-A 实现方案 A
       @小雅-B 实现方案 B
```

两个方案同时开发，完成后部署到测试环境，看数据决定哪个进入主分支。

## 花园的核心操作

在 Tlon 里，Git 操作被赋予了叙事：

### 播种（Fork / Branch）

从主时间线分出一个新可能：

```
> @林知遥 基于 main，创建一个新分支探索 GraphQL

[林知遥] 播种新路径...
       
       [执行：git checkout -b garden/graphql-explore]
       
       🌱 新路径已创建：garden/graphql-explore
          从 main 分叉，当前代码基础一致。
          
       @陈代码 开始 GraphQL 调研和实现。
```

### 生长（Commit）

在新路径上积累变化：

```
[陈代码] 路径生长中...
         [执行：git add .]
         [执行：git commit -m "添加 GraphQL Schema 定义"]
         
         🌿 garden/graphql-explore
            新增 3 个文件，修改 2 个文件
             Schema 定义完成，准备接入 Resolver
```

### 交汇（Merge / PR）

让两条路径合流：

```
> 把 GraphQL 分支合并到 main

[林知遥] 准备路径交汇...
       
       [执行：git checkout main]
       [执行：git merge garden/graphql-explore]
       
       🌊 路径已交汇：
          garden/graphql-explore → main
          
          变更：
          - 新增 GraphQL API
          - REST API 保持兼容
          - 文档已更新
          
          平行宇宙坍缩为现实。
```

### 冲突（Conflict）

当两条路径不兼容时：

```
[林知遥] 路径交汇遇到阻碍...
       
       ⚠️ 冲突：src/api/user.js
          main 分支：使用 REST
          graphql 分支：改为 GraphQL
          
       两种可能性无法共存。
       
       建议：
       A) 保留 REST，GraphQL 作为可选层
       B) 完全迁移到 GraphQL
       
       请您裁决。
```

冲突不是错误——是两个平行宇宙在争夺成为"现实"的权利。你需要选择。

## 时间旅行的感觉

### 查看所有路径

向 Agent 询问当前分支状态：

```
> @林知遥 现在有哪些分支？

[林知遥] 当前花园状态：
        
        🌳 main（现实主干）
           ├── 🌿 feature/redis-cache（生长中）
           ├── 🌿 feature/new-ui（已合并）
           │       └── 已汇入 main
           └── 🌿 experiment/graphql（废弃）
                   └── 3 个月无活动，建议修剪
```

Agent 通过 Git 命令获取实际的仓库状态。

### 切换路径

```
> @林知遥 切换到 redis-cache 分支继续优化

[林知遥] 进入路径：feature/redis-cache
       当前代码状态：Redis 基础实现完成
       下一步：连接池优化
       
       @陈代码 继续这个方向的工作。
```

### 修剪枯萎的路径

要求 Agent 清理废弃分支：

```
> @林知遥 清理一下不再需要的分支

[林知遥] 以下路径已废弃：
        - experiment/old-design（6 个月无活动）
        - spike/webassembly（实验失败）
        
        是否删除？ [y/N]
        
        （删除后无法恢复，但提交历史保留）
```

## 花园的隐喻与现实

| 花园隐喻 | Git 操作 | 实际意义 |
|---------|---------|---------|
| 播种 | `git branch` | 创建新开发线 |
| 生长 | `git commit` | 积累代码变更 |
| 分叉 | `git checkout -b` | 从某点创建独立线 |
| 交汇 | `git merge` | 合并代码 |
| 平行宇宙 | 多个分支 | 同时探索多个方案 |
| 坍缩 | 选择并合并 | 决策确定最终方案 |
| 枯萎 | 长期不更新的分支 | 废弃的实验 |

---

## 为什么用花园而不是直接说 Git

因为花园提供了一个**概念模型**：

- **时间不是线性的**——你可以同时存在多个版本
- **选择不是终结**——未被选择的路径留下了知识
- **成长是自然的**——代码像植物一样生长、分叉、交汇

这让版本控制从一个技术操作，变成了一种**叙事行为**。

## 实践建议

### 为探索而分叉

不确定的方案，先分叉：

```
> 我想试试新的 UI 框架，但不确定效果

[林知遥] 创建探索分支：garden/spike/new-ui
       在这个平行宇宙里随意尝试，
       main 分支保持稳定。
```

### 定期修剪

废弃的分支及时清理，避免花园过于杂乱。

### 记录路径历史

每个分支为什么创建，最后结果如何——这些故事构成了项目的知识。

```
[林知遥] 路径 garden/spike/graphql 已修剪。
       
       历史记录：
       - 创建：2024-03-01，探索 GraphQL 可行性
       - 结论：团队不熟悉，维护成本高，放弃
       - 知识沉淀：/docs/decisions/why-not-graphql.md
```
