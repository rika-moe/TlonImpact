## 这是什么样的未来

环形废墟的核心命题：**Agent 可以创造 Agent**。

### 你构想一个需求

```
> @林知遥 我们需要一个专门做数据清洗的 Agent

[林知遥] 我可以在镜中凝聚一个新的轮廓。
         CSV 为主，需要 pandas，性格细心严谨——对吗？

> 对

[林知遥] 正在创造...
        
        [镜子] "我是数据员小洁。"
        
        小洁已进入代表大会。
```

你不再需要手动打开 `tlon mirror`——团队成员自动扩展。

### 团队自我演进

随着项目复杂度增长，Agent 会根据工作负载建议分工：

```
[陈代码] 项目越做越大，建议创造新角色：
        前端专员（React）、后端专员（API）、测试专员
        
        是否授权？
```

### 临时专家

遇到团队不熟悉的领域，按需创建临时 Agent，任务完成后自动休眠。

## 设计蓝图

### 递归层级

```
你
├── 林知遥（PM）
│   ├── 陈代码（开发）
│   │   ├── 前端专员
│   │   └── 后端专员
│   └── 阿杰（产品）
└── 小夏（客服）
    └── 工单分发员
```

理论上，每个 Agent 都可创造子 Agent，形成职责树。

### 安全边界（草案）

设计中的保护机制：

1. **创造配额**：每个 Agent 每天最多创造 1 个子 Agent
2. **权限降级**：子 Agent 权限不超过父 Agent
3. **资源限制**：新 Agent 的 Docker 资源受总配额约束
4. **审计日志**：所有创造操作全程记录
5. **人工审查**：涉及权限提升的操作需人类确认

### 设计中的紧急制动

```
tlon ruins pause                    # 暂停所有创造
tlon ruins tree                     # 查看递归树
tlon ruins prune 陈代码 --children  # 销毁分支及所有子 Agent
```

## 为什么叫环形废墟

在博尔赫斯的同名小说中，一个魔法师在环形废墟中做梦，梦见自己创造了一个人——最后发现**自己也是别人的梦中人**。

环形废墟的递归命题：你创造 Agent → Agent 创造 Agent → 创造的链条没有起点和终点。谁是创造者，谁是被创造者？边界最终消融。

---

>
> "我在这里做梦，
>  梦见自己醒了，
>  发现自己在另一个梦里。
>
>  这是环形废墟。
>  没有起点，没有终点。
>
>  只有创造，
>  永恒地递归。"
