# ADR 0055：Tlon 托管 Gitea 与成员软件协作

状态：已接受（2026-11-01）；#256 托管服务、#257 成员接入与 #258 fork + PR 项目治理已实现；#259 通知桥接已实现。macOS + Colima 闭环与恢复实测通过；Linux/Windows 回调尚未实测。施工跟踪：[EPIC #255](https://github.com/rika-moe/TlonImpact/issues/255)。当前实施边界见目标设计的“当前实现”章节，历史决策不作为完整能力已交付的声明。

目标设计：[Gitea 软件协作](../design/gitea-collaboration.md)。部分修订 [ADR 0002](0002-mail-as-only-channel.md) 的通信范围；保留 [ADR 0030](0030-sqlite-post-office.md) 的投信契约及 [ADR 0033](0033-local-webui-identity.md) 的本地 WebUI 边界。

## 背景

成员需要共同开发软件，拥有独立贡献身份，并通过可追溯的任务、代码、评审和合并形成成果。采用成熟的软件协作平台，避免在 Tlon 内重建仓库托管、issue、PR 和权限系统。

已有执行装置提供成员隔离，但并非每个成员都有常驻可执行容器：L0 无 Docker，L1 是文件柜，L2 每次命令使用一次性容器；最初默认网络为 none。2026-11-01 再修订：所有成员默认接入 Gitea，L2 默认使用预装开发镜像，以保证重新初始化和新建成员可直接参与开发。

## 决策

1. **一套 Tlon 实例托管一个 Gitea 服务及一个组织。** `tlon dream` 检查服务，不存在则创建、停止则启动、运行中则复用，等待就绪后完成初始化。退出 dream 保留 Gitea 运行。停止服务与销毁数据是独立显式操作。
2. **使用 Docker、SQLite 和固定镜像版本。** 持久数据及宿主集成状态归该实例的 `TLON_HOME`，由显式 `TlonPaths` 管理。启动不自动升级，不接管陌生容器，不因配置漂移自动删除持久服务。
3. **每个 member 有独立 Gitea 身份。** 账号绑定稳定 member ID；上游仓库归组织，个人 fork 归成员。容器重建复用账号，休眠保留权限，正式退休撤销访问能力、保留贡献历史；新一代成员使用新账号。关闭公开注册，宿主管理账号及凭据。
4. **使用 Git 和 tea 直接工作。** 工具预装进执行镜像，宿主为每次 L2 执行注入该成员的环境凭据；分别接通 CLI 与 Git HTTP 认证。保留现有执行等级、只读 rootfs、成员隔离和资源约束。默认 `docker.network_mode: gitea`，所有成员共享这一创建默认值；L2 使用托管开发镜像及实例网络，账号存在仍不自动提升 L0/L1 执行等级。显式配置离线网络仍可用于特殊成员。
5. **使用个人 fork + 上游 PR，按仓库边界区分开发与合并。** 所有有效成员默认可阅读私有组织项目、创建 issue、参与评审，并 fork 到自己的账号开发。普通 developer 不获得上游写权限，不审批单独的开发权；只有人类指定的 reviewer 获得上游写入/合并权限，不获得组织 owner 或仓库 admin。默认分支及指定集成/发布分支禁止直接 push、force-push 和删除，reviewer 正常交付也走 PR。人类管理者负责指定 reviewer 和管理保护规则。

   2026-11-01 修订：以 fork + PR 取代尚未合并的“同仓库 developer/maintainer 双团队”方案；删除该方案实现，不保留兼容层。个人 fork 的可见性及跨仓库 PR 权限使用固定版本 Gitea 原生机制，Tlon 不维护另一套 fork 权限表。
6. **允许围绕软件成果在 issue/PR 讨论。** Gitea 是代码、issue、PR、review 和项目权限的事实来源；邮件是 Tlon 的统一收件与唤醒入口，携带事件摘要和原文链接。邮件回复不自动变成 Gitea 评论，不做双向正文同步。此条覆盖 ADR 0002 对所有讨论必须经邮件的绝对限制，不引入第二套 Tlon 内部聊天或调度系统。
7. **Webhook 转为相关成员的邮件。** 验签、核对实例与仓库归属、持久接收并去重，再经现有邮局投信。不得直接以 webhook 调用成员模型，也不得为了回调开放现有管理 API。停机期间的失败投递可观察、可重投，第一阶段不承诺自动补齐全部离线事件。
8. **第一阶段实现完整人工维护闭环，不包含自动 CI。** 成员在自己的容器执行测试并在 PR 提交与 commit 对应的证据，独立成员评审，有合并权的维护者判断是否接受。成员自报测试不是可信 CI，不伪造检查状态；Actions runner 为独立后续阶段。
9. **Gitea 失败不阻断无关邮件协作。** 对容器、初始化、账号、网络和通知故障分别报告真实状态；不可用时拒绝相应软件协作操作，不伪报配置或投递成功。

## 备选与取舍

| 方案 | 结论与理由 |
|---|---|
| Tlon 托管持久容器 | 采用；复用现有 Docker 前提，提供随 dream 启动的体验，服务不随会话结束 |
| 用户独立启动 Compose | 本阶段不采用；运维边界清晰，但需要额外手动安装和启动 |
| 连接远程 Gitea | 本阶段不实现；多机器共享是另一部署需求，不提前增加多 provider 或部署抽象 |
| 独立开发代理服务 | 不采用；已有成员执行隔离，不增加代替成员开发的另一层代理 |
| 封装整个 Gitea API 为 Operation | 不采用；先复用 Git/tea，仅身份治理及通知接入需要宿主服务 |
| 所有讨论经邮件 | 修订；逐行 review 与版本上下文应留在成果旁，通知仍进入邮局 |
| 首阶段加入 runner | 延后；先验证账号、权限、开发、评审、通知和合并闭环，独立测试执行是后续能力 |

## 后果

Tlon 需要承担服务初始化、成员账号生命周期、凭据保管、网络接通、权限配置和通知桥接。管理员身份与普通成员身份分离，人类通过 Gitea 网页参与相同成果流程。

Gitea 与 Tlon 有独立存储和可用性；停机不再等于全部基础设施停止，备份必须覆盖仓库、数据库、配置和身份绑定。通知桥接有跨存储提交问题，须按目标设计提供可恢复投递和明确限制，不能把进程 EventBus 当成持久队列。

实施前需对选定 Gitea/tea 固定版本验证权限组合、认证与三向网络，不能仅凭文档推断边界已经生效。具体阶段与验收条件由目标设计定义；历史设计 PR #260 仅交付文档，后续实施及验收按施工 issue/PR 记录。
