# ADR 0040：未执行草稿与预算通知的事实边界

状态：已实施（2026-10-18）。用户确认修复玄奘近期会话暴露的两处问题。

## 背景

发信草稿被 critique 拦截后，revise 只回传意见，不回传原草稿或明确的未执行状态。下一轮容易把评审措辞理解成已经发信。耗尽预算后，旧流程又从混合对话上下文生成回信，将未发送草稿描述成“前函”，绕过了常规交付评审。

## 决策

1. 评审输入明确区分待执行草稿与真实工具回执。对未派发邮件的修订反馈附完整草稿（调用编号、工具、收件人、正文等），明确“本轮调用已拦截，尚未执行/发送”。以普通文本消息保存草稿，不伪造 assistant tool_calls 或 tool 结果；原有 journal 记录和工具配对不变。评审标准不能把当前草稿当作历史已发信。
2. 仅有 FAIL 且意见为空时也必须告知拦截和未执行状态，不允许静默丢掉草稿。已执行后的自评与发信前门控必须区分，不能把已有真实回执的调用标成未执行。
3. 预算上限通知改为 runtime 的确定性进度报告，不再调用模型生成完成总结。不从自然语言、草稿、评审反馈或上下文摘要推导已发送事实，只依据本次会话实际工具结果和真实 mail_id/request_id 回执。区分确认提交、明确失败、结果未知；幂等重试不得按调用次数重复算成多封邮件。
4. 通知明确标记资源上限，告知工作未完成且草稿不代表已发送。通知自身与邮件工具的交付分开表述；本地入箱和网关尝试不等于阅读或外部送达。维持仅向责任集的人类发件人通知、按原邮件回复、幂等发送与结束原因 journal 的既有契约。
5. 不改当前 ~/.tlon 的人格、联系人、邮件、记忆或会话历史；不替玄奘发送更正/补发邮件。

## 验证

复现两封草稿同时被拦截、下一轮收到准确草稿与未执行说明、修订后仅发出新版本；验证 journal 可重建相同上下文。验证全程未发信、多封信部分成功、失败/未知和幂等重试的预算报告，并覆盖 iteration/token 两种上限。即使模型反馈写“已发送/前函”，也不能污染确定性通知或制造发件记录。

实施验证：`scripts/check_all.sh` 14/14 全绿，单测 2283 通过、15 跳过，集成测试 25 通过。独立临时 TLON_HOME 的真实 dream + SDK 传输 + 本地模型替身冒烟验证：两封草稿被拦截，均无实际投递；仅生成一封确认提交数为 0 的运行时通知，模型调用严格停在 think 与 critique 两次。临时进程、数据与端口均已清理。
