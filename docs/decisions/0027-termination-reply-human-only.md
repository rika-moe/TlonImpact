# ADR 0027：终止回复只发给人类触发者

> 阅读定位：本文保留当时的选择与理由；当前设计见 [runtime](../design/runtime.md)。当前适用范围：仅回复人类的抑制语义保留；单一触发者锚点由 ADR 0028 责任集替代。完整关系见 [决策索引](README.md)。

状态：已接受（2026-10-11 拍板）

## 背景

一次线上事故暴露了终止回复的振荡风险：DeepSeek 余额耗尽后，每次认知处理都以 permanent 4xx 失败 → `error_limit` 触发 `:until` 终止 → 引擎回复「抱歉，处理邮件时出现了错误。」→ 这封回复邮件投递给对方 agent，唤醒它的一个新 session → 对方同样失败、同样回一封错误回复 → 两个 agent 互相用错误回复唤醒对方，4 分钟产生 47 封垃圾邮件。

根因不在 LLM 故障本身（故障总会发生），而在**终止回复是一条新的触发邮件**：引擎的兜底反馈对「发件人是谁」一视同仁，把机器可自愈的失败状态变成了社会层面的新事件，振荡链条由此闭合。

## 决策

**所有终止回复，发送前看触发邮件的 from**：人类发件人照常回复（人需要反馈——沉默对人类是故障）；非人类发件人（agent、postmaster、外部地址）只记 journal（`session/end`，reason 不变）+ 一条 `termination_reply_suppressed` 日志（带 session_id、sender、reason），不发信。

覆盖全部三个终止回复发送点（`LoopDriver`）：

1. 引擎硬顶（max_iterations / max_tokens，ADR 0023）——抑制时连蒸馏回复的 LLM 调用也跳过（那是一次必然只为被抑制回信服务的调用）；
2. `_terminate_loop`（`:until` 触发：error_limit / iteration_limit）；
3. `send_failure_reply`（调度器异常终止：超时 / stage 未捕获错误）。

正常 act 完成的回复（`sendEmail is_complete=true`）不受影响——那是会话循环的正常产出，不是兜底反馈。配方 `:replies` 的措辞覆盖语义不变（人类触发时仍生效）。

「人类」的判定：构造器注入的 `is_human_sender` 闭包，基于 `TlonPaths.known_human_ids()`（有持久邮箱的人类 id）+ `address_for_member` 比对地址；每次判定实时重查，不缓存——人类集合随首次投递增长，且人类来信在处理时刻必然已落邮箱、必然已知。

## 修订

- **2026-10-11（ADR 0028 决策 7 修订锚点定义）**：触发邮件不复存在（收件箱驱动的单 session 模型），终止/失败回复的锚点从「触发邮件发件人」迁到「责任集」——异常终止时给责任集内每个人类发件人各发一封失败通知（按发件人地址去重，`in_reply_to` 取该发件人在责任集内最新一封）；责任集内的 agent 发件人维持本决策的抑制语义（只记 journal + `termination_reply_suppressed` 日志）。抑制语义本身不变。

## 否决的备选

- **熔断器 / 速率限制**（如 per-sender 或 per-thread 的发信频率上限）：能治振荡，但给所有通信引入策略参数，阈值无依据、可能误伤正常高频协作。留作以后——若人类侧或其他路径再出现风暴再议。
- **错误回复不带 `in_reply_to` / 另起线程**：对方仍会被新邮件唤醒，只是线程更乱，不解决触发问题。
- **终止回复一律不发**：对人类触发者也是沉默，人无法区分「处理中」与「已失败」，体验不可接受。

## 后果

- agent 间的失败振荡在源头断开：失败状态留在 journal 与日志里可排查，不再外溢为邮件事件。
- 人类触发者体验不变：超时、错误、资源到顶都有回信。
- 观测面：`termination_reply_suppressed` 日志是「终止了但没发信」的唯一痕迹，排查 agent 间交互时先看它。
- 已知边界：一个**尚未拥有邮箱**的人类（从未收发过信）不在 `known_human_ids()` 里，其触发会被按非人类抑制——但该状态不可能发生：人类来信在投递时即创建其邮箱。
