# 审阅原型提案

评审是成员的判断，是否调用模型以及如何组织步骤由普通 Lisp 程序或当前行动循环决定。以下步骤不要求额外模型调用，也不自动批准原型。

1. 用 `prototype-staging-list` 定位提案，再用 `prototype-read {"name": "提案 ID"}` 获取元数据、文件清单和 `digest`。不要把显示名当作技术 ID。
2. 按需调用 `prototype-read`，传入同一 `name`、返回的 `digest` 和清单中的 `path`。`offset` 是字符偏移，`limit` 默认及最大 12000；返回非空 `next_offset` 时按该偏移继续，直到读完相关材料。材料发生变化时重新获取清单并审阅，不能沿用旧结论。
3. 检查 behavior 入口、完整模块依赖、实际工具效果、执行层级是否必要、停止与错误处理、描述与行为是否一致；存在 `LESSONS.md` 时核对教训是否落实。如需比较父代，显式调用 `prototype-lineage`，谱系不会自动加入上下文。
4. 意见充分时，调用 `prototype-review-submit`，只传入 `name`、审阅材料的 `digest`、`verdict`（`通过`、`不通过`、`弃权`）和非空 `reason`。理由注明实际审阅的文件、证据、未验证的部分和关键风险。材料不足可弃权，也可以不提交。不要声称未执行的动态验证已经通过。
5. 提交成功仅表示意见已保存。人类决定是否批准；读写工具不会自动请求模型、创建成员或放宽权限。评审者、run、调用标识和时间由宿主记录，不填写或伪造这些字段，不把配置模型名称当作独立审查证据。

相同调用的恢复会读取已保存的回执，避免重复写入。收到未知结果时按运行时恢复机制核查原调用，不能新建调用后声称是同一次评审。
